# 0150 — Platforms checked without their hardware: simulated GPUs, Godot's three renderers, cross-built templates

Status: **KEEP** (diagnostics and fixes; `FELLOW_VULKAN_PROFILE` changes nothing unless set) · Branch `fellow/geometry`
· `drivers/vulkan/fellow_vulkan_profile.{h,cpp}`, `fellow_vulkan_profile_data.h` (generated), hooks in
`rendering_device_driver_vulkan.{h,cpp}` · Scripts: `benchmarks/tools/platforms/` (`renderer_matrix.sh` and `.py`,
`profile_matrix.sh`, `platforms.sh`, `Dockerfile.{cross,wine,arm64,android,web}`, `make_vulkan_profiles.py`,
`image_stats.py`).

## Problem

Godot exports to Windows, Linux (x86_64, arm64), macOS, Android, iOS and the web, with three renderers: Forward+ on
desktop GPUs, Mobile on Android and Quest, Compatibility (OpenGL 3.3 / ES 3.0 / WebGL 2) on the web and old GPUs. Every
FellowEngine change of milestones 1-48 was developed and measured on one Windows laptop (an NVIDIA RTX 5070 Ti Laptop
GPU, Vulkan, Forward+), and checked on lavapipe (Mesa's CPU Vulkan driver) with Forward+. The assessment
(`docs/fellow_aaa_readiness.md`) calls platforms and GPUs the largest gap: AMD and Intel GPUs never run, the Mobile and
Compatibility renderers never run with FellowEngine's changes, no other platform built. There is no other hardware:
the checks have to run on the one x86_64 Linux machine in the cloud, without a GPU (and without loading the laptop's).

## Change

**Simulated GPUs** (`FELLOW_VULKAN_PROFILE=<name>`, read once by the Vulkan driver). The driver presents its device as
another one, so that Godot and FellowEngine choose the paths they would choose there:

- extensions: only those the profile lists are seen (the diagnostic ones, debug utils and the like, always);
- features: `VkPhysicalDeviceFeatures` and the capability flags Godot reads (half floats, 8/16-bit storage, multiview,
  buffer device addresses, the memory model, ray queries and pipelines, cooperative matrices, variable rate shading,
  fragment density maps) ANDed with the profile's;
- limits: maxima lowered to the profile's, alignments raised to them, the API version lowered; subgroup operations and
  stages masked (the subgroup's size stays lavapipe's);
- formats: BC, ETC2 and ASTC usages masked as the profile has them; 32-bit image atomics off for Apple's.

Every shader is then checked against the simulated device when it is created — the SPIR-V's capabilities (each mapped
to the feature that enables it), the compute workgroup's size (`LocalSize`, `LocalSizeId`, `WorkgroupSize`) and shared
memory, and from the reflection the descriptors a stage, a layout and a set, the push constants and the uniform
buffers' ranges — and what the device could not run is printed once, when a pipeline is made from the shader, as
`FELLOW_PORTABILITY <profile>: <shader>:<variant> (<stage>) ...`. At pipeline creation, not at shader creation, because
Godot compiles every variant of a shader and makes pipelines of those the device's features select (FSR 1's half-float
variant is compiled on every device and used only where half floats exist).

The profiles are generated by `make_vulkan_profiles.py` from the Khronos Vulkan-Profiles repository's JSON (read as
data): Android's baseline profiles of 2022 and 2025 (what every Android device of that year guarantees), and device
captures from vulkan.gpuinfo.org — Intel UHD Graphics 620 and Arc A770, NVIDIA GTX 1060 and RTX 4070, AMD RX 580 and
RX 7800 XT, Apple M1 through MoltenVK — plus three single-family profiles (no ray tracing, no half floats, basic
subgroups only). A profile can only take away from lavapipe: lavapipe has no cooperative matrices, so nothing that
needs them runs under any profile.

**The renderer matrix** (`renderer_matrix.sh`; `renderer_matrix.py` for any OS, with images compared to a reference run): every bench lab (20 cases: the 16 labs, the streaming and world labs,
the storm and the snow) with Forward+ and Mobile on lavapipe and Compatibility on llvmpipe (OpenGL), under Xvfb, at
480 × 270; per run the exit status, the errors (unique messages), the image's mean and spread (a black or flat frame
shows), the portability lines. `profile_matrix.sh`: eight labs under each device profile (Android's with Mobile, the
others with Forward+).

**Other platforms in containers** (`platforms.sh`, Docker on the cloud machine): the Windows x86_64 export template with
MinGW-w64 (GCC 13, posix threads), run under Wine 9 — headless, and rendering through winevulkan on lavapipe or
through Wine's OpenGL on llvmpipe; the Linux arm64 template with GCC's aarch64 cross-compiler, run under qemu-user —
headless with the cross-compiler's libraries, rendering with Ubuntu's arm64 Mesa. The Android (NDK r29) and web
(Emscripten 4.0.10) templates have images and build commands, not run: their toolchains are downloads from Google and
GitHub this milestone did not make.

**Fixes found by the checks:**

- *A crash on every GPU without buffer device addresses.* `mesh_storage.cpp` declared the index buffers' creation flags
  as `BitField<RD::BufferCreationBits> fellow_rt_flags;` — BitField's default constructor leaves its value
  uninitialized, so index buffers asked at random for device addresses and acceleration-structure input. On lavapipe
  and the RTX those exist; under Android's profiles the buffer creation failed (`VK_ERROR_FEATURE_NOT_PRESENT`) and the
  next frame crashed. Now `= {}`.
- *The Mobile renderer's positional lights.* FellowEngine's light loop (shared by Forward+ and Mobile through
  `scene_forward_lights_inc.glsl`) skips lights whose attenuation is zero at the pixel (decision 0008) and back-facing
  positional lights (decision 0005) with early returns. In the Mobile renderer, where each light is a call in an unrolled loop, the
  pixel lost the lights after the first skipped one: the Lights Lab was 4 × darker than stock (mean 9.3 against 36.6),
  the Blend Lab 109.5 against 149.2. Found by bisecting the shader file's hunks against stock; the two skips are off
  in Mobile (`sc_fellow_zero_attenuation_skip()`, `sc_fellow_skip_backfacing_positional()` return false there), and
  Mobile's images are stock's again (36.6, 149.0).
- *Windows: stock Godot's DirectInput hook.* `OS_Windows::install_iat_hook` restores the import table's protection with
  `VirtualProtect(..., old_protect, nullptr)`. Windows fails that call (the last argument must point to a variable: the
  page stays writable); Wine 9 crashes on it, before `main()`. A variable for it now.
- *Varyings.* Godot's shader language counted varyings passed from `fragment()` to `light()` against the device's
  interpolants, which they are not (the compiler declares them as plain variables of the fragment stage); with
  Godot's Mobile renderer reserving 15 of the 16 that Vulkan's minimum of 64 vertex output components gives (Android's
  2022 baseline), the water shader (three varyings, one fragment-to-light) failed to compile. Those varyings are not
  counted now, and the water's two interpolated ones are one `vec4`.
- *Gas volumes.* The sparse simulation's activation and clearing kernels bind 11 and 10 storage images a stage;
  Android's 2025 baseline guarantees 8: on such a device the volumes are simulated dense (a warning) and those
  pipelines are not made. The trace pass read 3 × 8 volume textures through combined samplers (27 samplers a stage;
  MoltenVK on Apple's M1 reports 16): it reads textures through one sampler now.
- *Glow.* FellowEngine's 16 × 16 glow tiles (decision 0052, the default) need 256 invocations a workgroup, twice
  Vulkan's minimum: on a device with fewer the padded blur is used and the tiles' pipelines are not made.
- *A leak at exit.* MultiMesh culling's pool buffer (decision 0034) was never freed: every Forward+ scene with a
  MultiMesh ended with "1 RID of type StorageBuffer was leaked" (not in Mobile, not in stock).
- *Builds.* MinGW: `windows.h`'s `near`/`far` macros against locals and parameters (`fellow_lightning_3d.cpp`, texture
  streaming's camera, the scene cull), locals that shadow (`-Wshadow` is an error there), an enum compared to an
  unsigned, the FidelityFX SDK's `swprintf_s` (MSVC's). Clang: an `override` that the class's other overrides lack
  (228 warnings), a class declared twice.
- *The other renderers.* FellowEngine's RenderingDevice nodes (gas, burning, water, shallow water, rain) printed
  errors with the Compatibility renderer; they warn once now, saying what is missing, and the gas volume says that the
  Mobile renderer simulates it but does not draw it. The water shader used `textureQueryLevels()`, which the
  Compatibility renderer's GLSL ES 3.0 lacks.

## Verification

The renderer matrix and the profile matrix on the cloud's CPU (2 cores; Mesa 25.2.8, lavapipe and llvmpipe), the
Windows build under Wine 9.0 (Ubuntu 24.04's), the arm64 build under qemu-user 8.2. Stock Godot 4.7.2 (the fork's
base, with the profile code only) on the same profiles and labs, to tell stock's findings from FellowEngine's.

## Results

no non-zero exit in the 60 runs, and after the fixes no error in any (before them the Compatibility renderer's runs of
FellowEngine's labs printed 1-4 errors each). Forward+'s images are stock's where stock can run the lab (PBR Lab 150.6 against
stock's 150.9 mean, the spread 40.8 against 41.0; the others within 0.9). The Mobile renderer:

**Clang** (the compiler of Android's NDK, Emscripten and Apple's toolchains; Ubuntu's clang 18 with lld, a Linux
template, 1 h 44 min): it builds with no error; two warnings of FellowEngine's headers (an `override` the class's other

**Not checked**: performance anywhere but the RTX (a simulated device runs at lavapipe's speed), driver bugs, the

Direct3D 12 and Metal (FellowEngine's changes are in the Vulkan driver and RenderingDevice; Godot's Metal driver is
the default on Apple's platforms), Android and web templates (their toolchains not downloaded), macOS and iOS (Apple's
SDK), consoles.

## Decision

**KEEP.** For want of other machines, FellowEngine now runs, every lab, on Godot's three renderers, on nine simulated
GPUs and as Windows and arm64 builds, with no crash and Linux's images, and the checks found what one Windows laptop
could not: a crash on every GPU without buffer device addresses (Android's, older desktop ones), the Mobile renderer
losing positional lights, a Windows crash under Wine in stock's code (a failing call on Windows), limits of Android's
and Apple's devices that FellowEngine's gas, glow and water exceeded, a leak at exit, and two compilers' build errors
and warnings. On Android's 2025 baseline and on every desktop profile FellowEngine asks for nothing the device lacks;
on Vulkan's minimums (Android's 2022 baseline) stock's Mobile renderer does not fit either. `FELLOW_VULKAN_PROFILE`
stays as a diagnostic, the scripts as the platform checks to run after a change. What simulation cannot give — other
GPUs' speed and drivers, the subgroup sizes, Android's, the web's and Apple's builds, consoles — stays open: next, with
approval, the NDK and Emscripten builds in an emulator and a headless browser.
